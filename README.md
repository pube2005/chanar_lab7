## Хэсэг E: Дүгнэлт (debrief)

### 1. Аль аялал хамгийн үр дүнтэй байв — согог тус бүр аль аялалаар олдов?

Энэ session-д хамгийн үр дүнтэй аялал нь Couch Potato (хоосон оролт) байв — нийт олдсон согогийн хамгийн оныг энэ аялалаар олсон. Учир нь ном нэмэх формын заавал бөглөх дүрэм (Гарчиг, Зохиолч, Он) хэд хэдэн газар зөрчигдөж байсан: жишээ нь Зохиолч хоосон байхад ном нэмэгдэж байсан (BUG-01), мөн Он хоосон үед "undefined" гэж харагдаж байсан (BUG-02). Supermodel (GUI) аялалаар 2 согог олдов: урт гарчиг хүснэгтийг эвдэж байсан (BUG-03), Устгах товч улаан биш байсан (BUG-04). Saboteur (API) аялалаар 1 согог олдов: буруу JSON биетэй POST хүсэлтэд 400 биш 500 буцаж байсан (BUG-05). Хамгийн бага үр дүнтэй нь Saboteur байсан ч энэ нь API түвшний цорын ганц согогийг олсон тул заавал шаардлага хангахад чухал байв.

### 2. Charter-аас гадуур санамсаргүй юу олдов? Юу шалгагдаагүй үлдэв (дараагийн session-ийн charter)?

Charter-т заагаагүй ч санамсаргүй олдсон зүйл бол хайлтын талбар том/жижиг үсгийг ялгаж байсан (BUG-06) — би хайлтын талбарыг туршихдаа "harry" гэж бичихэд "Harry Potter" олдохгүй, харин "Harry" гэж бичихэд олдсон. Мөн "Нийт ном" тоолуур устгасны дараа шинэчлэгдэхгүй байсан (BUG-07) — энэ нь өгөгдлийн түвшний согог. Харин дараах зүйлс шалгагдаагүй үлдэв: (1) оны хязгаар 1000-2100-аас гадуур утга (жишээ нь 999, 2101, сөрөг тоо) — цаг хүрээгүй; (2) ижил гарчиг+зохиолчтой ном давхардуулахыг шалгаагүй; (3) устгах үйлдлийн баталгаажуулалтын мессеж; (4) олон ном зэрэг нэмэхэд гүйцэтгэлийн асуудал. Дараагийн session-ийн charter-т "Оны хязгаарын шалгалт ба давхардлын дүрэм" болон "Устгах үйлдлийн бүрэн урсгал" гэсэн 2 charter төлөвлөж болно.

### 3. Эдгээр согогийн аль нь Лаб 1-ийн Playwright автомат тестээр баригдах байсан бэ, аль нь зөвхөн хүний нүдээр олдох байсан бэ?

Лаб 1-ийн Playwright автомат тестээр баригдах байсан согогууд: BUG-01 (Зохиолч хоосон байхад ном нэмэгдэх) — учир нь Playwright-аар формыг хоосон орхиж, "Нэмэх" товч дараад, хүснэгтийн мөрийн тоо нэмэгдээгүй эсэхийг шалгаж болно. Мөн BUG-05 (API 400 биш 500 буцаах) — Playwright-аар API хүсэлт илгээж, статус код шалгаж болно. Харин зөвхөн хүний нүдээр олдох байсан согогууд: BUG-03 (урт гарчиг хүснэгтийг эвдэх) — энэ нь визуал layout-ийн асуудал тул скриншот харьцуулалтгүйгээр автоматаар барихад хэцүү; BUG-04 (Устгах товч улаан биш) — өнгөний шалгалтыг автоматаар хийж болох ч Playwright-д CSS утга шалгах нь эмзэг (brittle) тест болдог; BUG-06 (хайлт том/жижиг үсэг ялгах) — үүнийг автоматаар шалгаж болох ч хэрэглэгчийн хүлээлттэй харьцуулах нь хүний үнэлгээ шаарддаг; BUG-02 ("undefined" харагдах) — энэ нь мессежийн текстэн дэх логик алдаа тул хүний нүдээр илүү хурдан олддог. Ерөнхийдөө автомат тест нь тодорхой, давтагдах боломжтой функциональ шаардлагыг шалгахад тохиромжтой, харин exploratory тест нь визуал, UX, логик зөрчлийг олоход илүү үр дүнтэй гэдгийг энэ session харуулсан.
